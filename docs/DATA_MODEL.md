# DATA_MODEL — Source of Truth

PostgreSQL. Drizzle schema in `src/server/db/schema.ts` must match this file. Change this file first, then the schema, then generate a migration.

## Global conventions

- Primary keys: `uuid`, default `gen_random_uuid()`.
- Every user-owned table has `user_id uuid not null` referencing the auth user, indexed, with `on delete cascade`.
- Timestamps: `created_at`, `updated_at` as `timestamptz not null default now()`. `updated_at` set by the app on update.
- Soft delete: `deleted_at timestamptz null` where noted.
- Money: `bigint` in **minor units** (centavos/cents) named `*_minor`. Currency as ISO 4217 `char(3)`.
- Calendar dates: `date`, not timestamps.
- Enums as Postgres enums.

## Auth tables

Owned and generated by Better Auth (`user`, `session`, `account`, `verification`). Do not hand-edit. The app's `user_id` columns reference `user.id`.

## Enums

- `transaction_type`: `income`, `expense`
- `invoice_status`: `draft`, `sent`, `paid`, `overdue`, `void`
- `recurrence_interval`: `weekly`, `monthly`, `quarterly`, `yearly`

### invoices (Phase 3)

| Column                 | Type                    | Notes                                                         |
| ---------------------- | ----------------------- | ------------------------------------------------------------- |
| id                     | uuid PK                 | default gen_random_uuid()                                     |
| user_id                | uuid FK → user.id       | not null, cascade on delete                                   |
| client_id              | uuid FK → clients.id    | not null; client must belong to user and not be archived      |
| project_id             | uuid FK → projects.id   | nullable; if set, must belong to user and match client_id     |
| category_id            | uuid FK → categories.id | nullable; if set, category.type must be 'income'              |
| number                 | text                    | not null, 1–50 chars; unique per `(user_id, lower(number))`   |
| amount_minor           | bigint                  | not null, `> 0` (check constraint)                            |
| currency               | char(3)                 | not null, ISO 4217 uppercase                                  |
| issued_on              | date                    | not null                                                      |
| due_on                 | date                    | not null, check `due_on >= issued_on`                         |
| status                 | invoice_status          | not null, default `'draft'` ('draft', 'sent', 'paid', 'void') |
| paid_on                | date                    | nullable; populated when status becomes 'paid'                |
| notes                  | text                    | nullable                                                      |
| created_at, updated_at | timestamptz             | not null                                                      |

Constraints & Indexes:

- Check constraint: `invoices_amount_minor_check`: `amount_minor > 0`
- Check constraint: `invoices_due_date_check`: `due_on >= issued_on`
- Unique index: `invoices_user_number_unique_idx`: `(user_id, lower(number))`
- Index: `invoices_user_status_idx`: `(user_id, status)`
- Index: `invoices_user_client_idx`: `(user_id, client_id)`
- Index: `invoices_user_due_on_idx`: `(user_id, due_on desc)`

Read-time derivation:

- `overdue`: derived at read time when stored `status == 'sent'` and `due_on < today`. The database column stores the canonical lifecycle state (`draft`, `sent`, `paid`, `void`); `overdue` is never written by a cron job (per Decision D-005).

### recurring_rules (Phase 3)

| Column                 | Type                | Notes                                                              |
| ---------------------- | ------------------- | ------------------------------------------------------------------ |
| id                     | uuid PK             | default gen_random_uuid()                                          |
| user_id                | uuid FK → user.id   | not null, cascade on delete                                        |
| interval               | recurrence_interval | not null ('weekly', 'monthly', 'quarterly', 'yearly')              |
| next_run_on            | date                | not null; next scheduled generation date                           |
| ends_on                | date                | nullable; check `ends_on is null or ends_on >= next_run_on`        |
| active                 | boolean             | not null, default true; false when cancelled or past ends_on       |
| template               | jsonb               | not null; transaction fields minus date and id (validated via Zod) |
| created_at, updated_at | timestamptz         | not null                                                           |

Template schema (`jsonb`):

```json
{
  "type": "income" | "expense",
  "amountMinor": 100000,
  "currency": "PHP",
  "categoryId": "uuid",
  "clientId": "uuid" | null,
  "projectId": "uuid" | null,
  "description": "Monthly Retainer",
  "paymentMethod": "bank" | null,
  "notes": "Contract retainer" | null
}
```

Constraints & Indexes:

- Check constraint: `recurring_rules_ends_on_check`: `ends_on is null or ends_on >= next_run_on`
- Index: `recurring_rules_user_active_next_run_idx`: `(user_id, active, next_run_on)`
- Index: `recurring_rules_user_next_run_idx`: `(user_id, next_run_on)`

Recurrence Advancement Rules:

- `weekly`: `next_run_on + 7 days`
- `monthly`: `next_run_on + 1 month` (clamped to the last valid day of month, e.g. Jan 31 → Feb 28/29)
- `quarterly`: `next_run_on + 3 months` (clamped to month end)
- `yearly`: `next_run_on + 1 year` (Feb 29 on leap year → Feb 28 on non-leap year)
- When `ends_on` is reached and `next_run_on > ends_on`, set `active = false`.

## Relationships

```
user 1─* clients 1─* projects
user 1─* categories
user 1─* invoices 1─0..1 transactions (income created on mark-paid)
user 1─* recurring_rules 1─* transactions (transactions generated on schedule)
user 1─* transactions *─1 categories
transactions *─0..1 clients, projects, invoices, recurring_rules
user 1─1 user_settings
```

## Integrity rules (enforced in services, mirrored by DB constraints where possible)

1. All referenced rows (category, client, project, invoice, recurring_rule) must belong to the same `user_id` as the transaction.
2. `category.type == transaction.type` (and `invoice.category_id` must be an income category).
3. Archived categories/clients cannot be chosen for new transactions/invoices but remain on existing records.
4. Soft-deleted transactions are excluded from every list and total. Purge after 30 days via a scheduled job (Phase 4).
5. Invoices:
   - When an invoice is marked paid, an income transaction is generated with `invoice_id = invoice.id`, `occurred_on = paid_on`, and `amount_minor = invoice.amount_minor`.
   - Invoices in `paid` or `sent` status with transactions cannot be hard-deleted (return `409 CONFLICT`; caller must void).
6. Recurring rules:
   - Deleting a recurring rule sets `recurring_rule_id = null` on past generated transactions (no cascade deletion of transaction history).

- Never edit an applied migration; add a new one.
